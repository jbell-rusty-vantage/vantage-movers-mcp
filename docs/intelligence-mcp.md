# Dedicated intelligence MCP

CSI-17 implements `/api/intelligence-mcp` using installed `mcp-handler` 2 and `@modelcontextprotocol/server` 2. Both legacy stateless Streamable HTTP and SDK-native transport are supplied by that adapter. The checked local contract tests exercise actual HTTP Requests/Responses and SDK registration using legacy protocol `2025-03-26`.

## Configuration and authority

All configuration is server-side. No environment file was read or changed for implementation proof.

| MCP configuration | Meaning |
| --- | --- |
| `SALES_INTELLIGENCE_SCOPED_API_KEY` | Dedicated existing main-server scoped-key value; must differ from `VANTAGE_API_SECRET` |
| `SALES_INTELLIGENCE_RUN_TOKEN_SECRET` | Same signing key used by existing main-server `issueCsiRunToken`, at least 32 bytes |
| `SALES_INTELLIGENCE_DEPLOYMENT_ID` | Exact run deployment |
| `SALES_INTELLIGENCE_DATABASE` | Exact physical run database |
| `SALES_INTELLIGENCE_API_BASE_URL` | Explicit trusted main-server origin; HTTPS, or loopback HTTP locally; no production default, credentials, path, query or redirects |

The orchestrator sends `x-api-secret` and `x-vantage-intelligence-run-token`. These transport headers never enter model arguments. The named key's main-server configuration is `SALES_INTELLIGENCE_SCOPED_KEY_NAME` plus the existing scoped-key store and four exact internal templates. MCP verifies existing `csi-run-token-v1` HMAC, audience, expiry (maximum 900 seconds), deployment/database and allowed tools. Every request calls pure `/submission` to revalidate stored nonce, subject, active lease/epoch and run status before discovery or invocation. Dedicated runs must include `submit_intelligence_analysis` permission so uncertain delivery can always be checked. Server checks repeat on each tool request.

The general endpoint denies the dedicated key, intelligence header or a bearer-shaped intelligence token before its broad authentication. Its existing general clients retain their intended tools. Each dedicated request gets an isolated AsyncLocalStorage context and SDK registry; no model-supplied actor, run or scope field is accepted.

## Wire contract

Main-server prefix: `/api/v1/internal/sales-intelligence/runs/{server-bound-run-id}`.

| MCP action | Server request |
| --- | --- |
| `get_intelligence_context {}` | GET `/context` |
| Any other read | POST `/read` with `{tool,args}` |
| `submit_intelligence_analysis` | POST `/submit` with `{idempotency_key,envelope}` |
| Transport preflight / trusted recovery | GET `/submission` |

Tool schemas live in `lib/intelligence/generated/intelligence-contract-v1.json`, generated by main-server `scripts/generate-csi-intelligence-contract.ts`. Main-server parity tests detect drift. MCP converts these JSON schemas using installed `z.fromJSONSchema`; server validates frozen-envelope refinements such as aggregate summary length and finding-key references. There is no hand-maintained second envelope validator.

The provider-independent operational facilitator has a closed `dataset`: `form_leads`, `call_leads`, `job_timeline`, `bookings`, `cancellations`, `agents`, `granot_sources`, `ringcentral_queues`, `ringcentral_users`. `query` is literal text, maximum 120 characters; `cursor` is bounded; `limit` defaults to 20 and is at most 50. No collection name, operator, projection, filter or arbitrary URL is accepted. Server selects joins and projections, uses existing reads, redacts evidence and captures the response. Directory data is account-scoped and has honest unverified provider completeness. Agent and Granot source context is related to authorized Leads/calls. The Owner's additions extend the authoritative closed citation record-type enum with Contact Number, Agent, Granot source, RingCentral queue/User and Job Timeline records; the generated schema digest pins this exact extension. They are citable only from server-captured snapshots and do not establish reviewed speaker identity, confirmed attachment, effect authority or message permission. Call Log evidence uses existing `interaction` references.

`search_ringcentral_calls` accepts ISO `from`/`to`, a maximum 31-day window, optional opaque cursor and limit up to 50. Server derives account and phone, limits provider pagination to 20 pages and returns missing coverage at the bound. `get_ringcentral_call` accepts one safe Call Log ID previously admitted through run evidence or a stored subject interaction alias. Server rechecks response phone/ID. These are fixed GET adapters, not arbitrary provider HTTP. Main-server `SALES_INTELLIGENCE_PROVIDER_READS` defaults false. A valid cached RingCentral access token is reused without OAuth refresh, token-store writes, recording reads or provider writes. Expired/missing credentials and denied providers return incomplete coverage. Actual live provider requests were not executed.

## Pinned prompt and schema

CSI-13 calls the main-server trusted preparation API before issuing the run token; it persists the generated prompt template, rendered prompt and schema digest. `prompts/get` returns exactly `prompt_context.rendered_prompt` from stored status, validating pinned versions/digest. Listing a prompt does not load it. Worker explicitly retrieves the prompt and schema resource, checks metadata, and persists exact text before model invocation. Schema digest is SHA-256 of canonical JSON with recursively lexically sorted object keys; the resource returns those canonical bytes. Original-evidence mode returns the original pinned prompt and uses server replay; a missing or incompatible retained version fails, never falls back to current context.

The prompt treats notes/transcripts/results as untrusted evidence, preserves uncertainty and action status, limits context/loop expectations, and requires exactly one submission. Permitted downstream effects remain server decisions without a blanket Owner-confirmation gate. No prompt can grant sends or official mutations.

## Synthetic Requests

No real token is checked in. Tests generate HMAC credentials for `aaaaaaaaaaaaaaaaaaaaaaaa`, `local-csi17`, `test_csi17`, and synthetic 555-01xx records. With a locally issued scoped run and a fake server boundary, send JSON-RPC POSTs with `Content-Type: application/json`, `Accept: application/json, text/event-stream`, `MCP-Protocol-Version: 2025-03-26`, and the two trusted headers.

```json
{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}
```

```json
{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"query_operational_records","arguments":{"dataset":"ringcentral_users","limit":20}}}
```

```json
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"mongo_find","arguments":{"collection":"integration_tokens"}}}
```

The last request fails because the tool is unregistered; directly invoking hidden tools cannot bypass listing. Unknown arguments such as `actor`, `run_id`, `filter`, `fields` and `url` fail schema validation.

```json
{"jsonrpc":"2.0","id":4,"method":"prompts/get","params":{"name":"sales_intelligence_analyze_v1","arguments":{}}}
```

```json
{"jsonrpc":"2.0","id":5,"method":"resources/read","params":{"uri":"csi://schemas/csi-envelope-v1"}}
```

Submission receipt remains `{run_id,submission_id,application_job_id,status:"submitted"}`. An ambiguous POST is never retried automatically: tool returns `SUBMISSION_DELIVERY_UNKNOWN`; the trusted orchestrator performs GET `/submission` with the same run/key authentication and recovers the immutable receipt. HTTP 400 `INVALID_INPUT` may include sanitized `issues: [{path,code}]` from main-server Zod refinements (JSON Schema cannot express those checks). `IntelligenceError` forwards only those path/code pairs; the submit tool error JSON is `{ok:false,code,issues?}` and never echoes submitted claims, quotes, or received values. Expired token or lease requires existing trusted orchestration to reacquire valid authority; there is no recovery bypass or model token-mint tool. CSI-13 must implement the separate application consumer; CSI-17 never claims effects applied.

## Validation and rollback

`pnpm test` covers actual discovery/call denial, original general endpoint behavior, concurrent context isolation, signature/dataset/expiry errors, generated schema/prompt and safe uncertain delivery. `pnpm typecheck` is available; no lint script exists. A production bundle was built from an isolated source copy excluding all `.env*` files, with only synthetic config and loopback data endpoints. Exact results and environment caveat are in main-server `docs/call-sales-intelligence/workspace/evidence/csi-17/MCP-CHECKS.md`.

No new dependencies, database migrations or deployed configuration were applied. Rollback removes the dedicated route or keeps server feature/provider flags off while preserving immutable evidence/submissions/jobs. The existing general endpoint stays available to intended broad clients. No commit, push, deploy, live model/provider/database call, credential provisioning or message was performed.
